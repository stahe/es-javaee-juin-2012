    12. Versión 7: aplicación web PAM con múltiples vistas y páginas

    Aquí volvemos a la arquitectura inicial en la que se simulaba la capa [de negocio]. Ahora sabemos que esta puede sustituirse fácilmente por la capa [de negocio] real. La capa [de negocio] simulada facilita las pruebas.

    Una aplicación JSF es de tipo MVC (Modelo-Vista-Controlador):

    • el [Faces Servlet] es el controlador genérico proporcionado por JSF. Este controlador se amplía mediante controladores de eventos específicos de la aplicación. Los controladores de eventos encontrados hasta ahora eran métodos de clases que servían como modelos para las páginas JSF
    • Las páginas JSF envían respuestas al navegador del cliente. Estas son las vistas de la aplicación.
    • Las páginas JSF contienen elementos dinámicos conocidos como el modelo de página. Tenga en cuenta que, para algunos autores, el modelo abarca las entidades manipuladas por la aplicación, como las clases PayrollSheet o Employee. Para distinguir entre estos dos modelos, podemos referirnos al modelo de aplicación y al modelo de página JSF.

    En la arquitectura JSF, la transición de una página JSFi a una página JSFj puede resultar problemática.

    • Se ha mostrado la página JSFi. Desde esta página, el usuario activa un POST a través de algún evento [1]
    • En JSF, esta solicitud POST suele ser gestionada [2a,2b] por un método C del modelo Mi de la página JSFi. Podemos decir que el método C es un controlador secundario.
    • Si, al final de este método, es necesario mostrar la página JSFj, el controlador C debe:
    1. actualizar [2c] el modelo Mj de la página JSFj
    2. devolver [2a] al controlador principal la clave de navegación que permitirá mostrar la página JSFj

    El paso 1 requiere que el modelo Mi de la página JSFi tenga una referencia al modelo Mj de la página JSFj. Esto complica un poco las cosas, haciendo que los modelos Mi dependan unos de otros. De hecho, el gestor C del modelo Mi que actualiza el modelo Mj debe conocer este último. Si es necesario cambiar el modelo Mj, también habrá que cambiar el gestor C del modelo Mi.

    Hay un caso en el que se pueden evitar las dependencias entre modelos: cuando hay un único modelo M utilizado por todas las páginas JSF. Esta arquitectura solo es adecuada para aplicaciones con pocas vistas, pero es muy fácil de usar. Es la que estamos utilizando actualmente.

  // list of employees

  public List<Employe> findAllEmployes() {

      // create a list of three employees
      listEmployes=new ArrayList<Employe>();
      listEmployes.add(new Employe("254104940426058","Jouveinal","Marie","5 rue des oiseaux","St Corentin","49203",new Indemnite(2,2.1,2.1,3.1,15)));
      listEmployes.add(new Employe("260124402111742","Laverti","Justine","La brûlerie","St Marcel","49014",new Indemnite(1,1.93,2,3,12)));
