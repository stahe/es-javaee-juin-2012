    5.2. Método de cálculo del salario de una cuidadora infantil

    A continuación, presentaremos el método para calcular el salario mensual de una cuidadora infantil. No se pretende que este sea el método utilizado en la práctica. A modo de ejemplo, utilizaremos el salario de la Sra. Marie Jouveinal, que trabajó 150 horas repartidas en 20 días durante el periodo de pago.

    Se tienen en cuenta los siguientes factores:
    
[TOTALHOURS]: total de horas
trabajadas durante el mes

    
[TOTALDAYS]: total de días trabajados
en el mes

    [TOTALHOURS]=150
[TOTALDAYS] = 20
    El salario base del cuidador infantil
    se calcula mediante la siguiente fórmula:
    [SALARIOBASE]=([TOTALHORAS]
*[TARIFA POR HORA])*(1+
[CPALLOWANCE]/100)

    [SALARIOBASE]=
(150*[2,1])*(1+0,15)= 362,25
    De este salario base
    deben deducirse de este salario base
    :
    
la cotización social general y
contribución para la amortización de la
deuda social:
 [SALARIOBASE]*[CSGRDS/100]

    
Contribución social general deducible:
 [SALARIO BASE]*[CSGD/100]

    
Seguridad social, prestaciones de viudedad y de vejez:
 [SALARIO BASE]*[SECU/100]

    
Pensión complementaria + AGPF +
Seguro de desempleo:
 [SALARIO BASE]*[PENSIÓN/100]

    CSGRDS: 12,64

    CSGD: 22,28

    Seguridad Social: 34,02

    Pensión: 28,55
    Total de cotizaciones a la Seguridad Social:
    [CONTRIBUCIONES SOCIALES] =
[SALARIOBASE]*(CSGRDS+CSGD
+SECU+PENSION)/100

    [CONTRIBUCIONES SOCIALES]=97,48
    Además, la cuidadora tiene derecho a una asignación para gastos de manutención y a una asignación para comidas por cada día trabajado. Por lo tanto, recibe las siguientes asignaciones:
    [Subsidios] = [TOTAL DE DÍAS]
*(SUBSIDIO DIARIO + SUBSIDIO DIARIO DE COMIDA)

    [DIENESTOS]=104
    Al final, el salario neto que se pagará al cuidador infantil es el siguiente:
    [SALARIO BASE] - [CONTRIBUCIONES A LA SEGURIDAD SOCIAL] + [PRESTACIONES]

    [SALARIO NETO]=368,77

    5.6. Implementación de JPA

    5.6.1. Capa JPA / Hibernate

    Configuraremos la capa JPA en el siguiente entorno:

    Un programa de consola interactivo funcionará con la base de datos. Para ello, necesitas:

    • disponer de una base de datos,
    • disponer del controlador JDBC para el SGBD, en este caso MySQL,
    • implementar la capa JPA utilizando Hibernate,
    • escribir el programa de consola.

    Creamos el proyecto Maven [mv-pam-jpa-hibernate] [1]:

    En la arquitectura de nuestra aplicación, necesitamos los siguientes elementos:

    • la base de datos,
    • el controlador JDBC para el SGBD MySQL,
    • la capa JPA/Hibernate (entidades y configuración),
    • el programa de la consola de pruebas.

    5.6.1.1. La base de datos

    En primer lugar, creemos una base de datos vacía. Iniciamos WampServer y utilizamos la herramienta PhpMyAdmin [1]:

    • en [2], selecciona la opción [Bases de datos],
    • en [3], cree una base de datos llamada [dbpam_hibernate],
    • en [4], se crea la base de datos.

    5.6.1.2. Configuración de la capa JPA

    La conexión entre la capa JDBC y la base de datos se configura en el archivo [persistence.xml], que configura la capa JPA. Este archivo se puede crear utilizando NetBeans:

    • en la pestaña [Servicios] [1], conéctese a la base de datos utilizando el controlador JDBC de MySQL [2],
    • en [3], el nombre de la base de datos a la que desea conectarse.
    • en [4], la URL JDBC de la base de datos,
    • en [5], inicia sesión como root sin contraseña,
    • en [6], puedes probar la conexión,
    • en [7], la conexión se ha realizado correctamente.
    • La conexión aparece en [8] y [9],
    • en [10], añade un nuevo elemento al proyecto,
    • en [11] selecciona la categoría [Persistencia] y en [12] el elemento [Unidad de persistencia],
    • en [13], asigne un nombre a esta unidad de persistencia,
    • en [14], seleccionamos una implementación de Hibernate,
    • en [15], especifica la conexión que acabamos de crear con la base de datos MySQL,
    • En [16], especifique que, cuando se instancie la capa JPA, debe crear las tablas correspondientes a las entidades JPA del proyecto.

    Al finalizar el asistente, se genera el archivo [persistence.xml]:

    • el archivo aparece en una nueva rama del proyecto, en una carpeta [META-INF] [1],
    • que se corresponde con la carpeta [src/main/resources] del proyecto [2,3].

    Su contenido es el siguiente:

    
<?xml version="1.0" encoding="UTF-8"?>
<persistence version="2.0" xmlns="http://java.sun.com/xml/ns/persistence" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xsi:schemaLocation="http://java.sun.com/xml/ns/persistence http://java.sun.com/xml/ns/persistence/persistence_2_0.xsd">
  <persistence-unit name="mv-pam-jpa-hibernatePU" transaction-type="RESOURCE_LOCAL">
    <provider>org.hibernate.ejb.HibernatePersistence</provider>
    <properties>
      <property name="javax.persistence.jdbc.url" value="jdbc:mysql://localhost:3306/dbpam_hibernate"/>
      <property name="javax.persistence.jdbc.password" value=""/>
      <property name="javax.persistence.jdbc.driver" value="com.mysql.jdbc.Driver"/>
      <property name="javax.persistence.jdbc.user" value="root"/>
      <property name="hibernate.cache.provider_class" value="org.hibernate.cache.NoCacheProvider"/>
      <property name="hibernate.hbm2ddl.auto" value="create-drop"/>
    </properties>
  </persistence-unit>
</persistence>
    • Línea 3: el nombre de la unidad de persistencia y el tipo de transacción. RESOURCE_LOCAL indica que el proyecto gestiona las transacciones por sí mismo. En este caso, el programa de consola se encargará de hacerlo,
    • línea 4: la implementación de JPA utilizada es Hibernate,
    • líneas 6-9: las propiedades JDBC para la conexión a la base de datos,
    • línea 11: solicita la creación de las tablas correspondientes a las entidades JPA. De hecho, NetBeans genera aquí una configuración incorrecta. La configuración debería ser la siguiente: 
    
      <property name="hibernate.hbm2ddl.auto" value="create"/>

    Con la opción create, Hibernate, al instanciar la capa JPA, elimina y luego crea las tablas correspondientes a las entidades JPA. La opción create-drop hace lo mismo, pero, al final del ciclo de vida de la capa JPA, elimina todas las tablas. Hay otra opción:

    
      <property name="hibernate.hbm2ddl.auto" value="update"/>

    Esta opción crea las tablas si no existen, pero no las elimina si ya existen.

    Añadiremos tres propiedades más a la configuración de Hibernate:

    
      <property name="hibernate.show_sql" value="true"/>
      <property name="hibernate.format_sql" value="true"/>
<property name="use_sql_comments" value="true"/>

    Estos ajustes indican a Hibernate que muestre las sentencias SQL que envía a la base de datos. Por lo tanto, el archivo completo queda así:

    
<?xml version="1.0" encoding="UTF-8"?>
<persistence version="2.0" xmlns="http://java.sun.com/xml/ns/persistence" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xsi:schemaLocation="http://java.sun.com/xml/ns/persistence http://java.sun.com/xml/ns/persistence/persistence_2_0.xsd">
  <persistence-unit name="mv-pam-jpa-hibernatePU" transaction-type="RESOURCE_LOCAL">
    <provider>org.hibernate.ejb.HibernatePersistence</provider>
    <class>jpa.Cotisation</class>
    <class>jpa.Employe</class>
    <class>jpa.Indemnite</class>
    <properties>
      <property name="javax.persistence.jdbc.url" value="jdbc:mysql://localhost:3306/dbpam_hibernate"/>
      <property name="javax.persistence.jdbc.password" value=""/>
      <property name="javax.persistence.jdbc.driver" value="com.mysql.jdbc.Driver"/>
      <property name="javax.persistence.jdbc.user" value="root"/>
      <property name="hibernate.cache.provider_class" value="org.hibernate.cache.NoCacheProvider"/>
      <property name="hibernate.hbm2ddl.auto" value="create"/>
      <property name="hibernate.show_sql" value="true"/>
      <property name="hibernate.format_sql" value="true"/>
      <property name="use_sql_comments" value="true"/>
    </properties>
  </persistence-unit>
</persistence>

    Las líneas 27-29 definen la clave externa de la tabla [EMPLOYEES] a la tabla [INDEMNITIES]. El atributo fetch de la línea 27 define la estrategia de recuperación para el campo indemnity de la línea 29. Hay dos modos:

    • FetchType.LAZY: Cuando se consulta a un empleado, no se recupera la indemnización correspondiente. Se recuperará cuando se haga referencia al campo [Employee].indemnity por primera vez.
    • FetchType.EAGER: Cuando se busca a un empleado, se recupera la indemnización correspondiente. Este es el modo predeterminado cuando no se especifica ningún modo.

    Para comprender la ventaja de la opción FetchType.LAZY, considere el siguiente ejemplo. En una página web se muestra una lista de empleados sin su remuneración, con un enlace [Detalles]. Al hacer clic en este enlace, se muestra la remuneración del empleado seleccionado. Vemos que:

    • Para mostrar la primera página, no necesitamos los datos de los empleados ni sus prestaciones. Por lo tanto, el modo FetchType.LAZY es el adecuado;
    • para mostrar la segunda página con los detalles, hay que realizar una consulta adicional a la base de datos para recuperar las prestaciones del empleado seleccionado.

    El modo FetchType.LAZY evita recuperar demasiados datos que la aplicación no necesita de inmediato. Veamos un ejemplo.

    5.8. La clase [PamException]

    La capa [DAO] funcionará con la API JDBC de Java. Esta API lanza excepciones [SQLException] controladas, lo cual tiene dos inconvenientes:

    • sobrecarguen el código, que debe gestionar estas excepciones mediante bloques try/catch.
    • deben declararse en las firmas de los métodos de la interfaz [IDao] utilizando «throws SQLException». Esto impide la implementación de esta interfaz por parte de clases que lanzarían una excepción controlada de un tipo distinto a [SQLException].

    Para solucionar este problema, la capa [DAO] solo «propagará» excepciones no controladas de tipo [PamException].

    • La capa [JDBC] lanza excepciones de tipo [SQLException]
    • La capa [JPA] lanza excepciones específicas de la implementación de JPA que se esté utilizando
    • la capa [DAO] lanza excepciones no capturadas de tipo [PamException]

    Esto tiene dos consecuencias:

    • La capa [business] no tendrá que gestionar las excepciones de la capa [DAO] mediante bloques try/catch. Simplemente puede dejar que se propaguen hasta la capa [UI].
    • Los métodos de la interfaz [IDao] no necesitan especificar la naturaleza de la [PamException] en sus firmas, lo que deja abierta la posibilidad de implementar esta interfaz con clases que lanzarían otro tipo de excepción no capturada.

    • La capa [DAO] encapsulará cualquier excepción encontrada dentro de una [PamException] y la volverá a lanzar a la capa [business].

    Una vez que la capa [DAO] ha sido probada y se ha considerado correcta, podemos pasar a probar la capa [de negocio] y el propio proyecto en su versión de consola o gráfica. Si, en el caso de prueba, la capa [ui] espera una [PamException] porque se creó con Hibernate, dejará de funcionar al cambiar a EclipseLink.
