    2. Arquitectura por capas de una aplicación Java

    Una aplicación Java suele dividirse en capas, cada una con una función bien definida. Consideremos una arquitectura común, la arquitectura de tres capas:

    • La capa [1], denominada aquí [ui] (interfaz de usuario), es la capa que interactúa con el usuario a través de una interfaz gráfica de usuario Swing, una interfaz de consola o una interfaz web. Su función es proporcionar datos del usuario a la capa [2] o presentar al usuario los datos proporcionados por la capa [2].
    • La capa [2], denominada aquí [business], es la capa que aplica las denominadas reglas de negocio —es decir, la lógica específica de la aplicación— sin preocuparse por el origen de los datos que recibe ni por el destino de los resultados que produce.
    • La capa [3], denominada aquí [DAO] (objeto de acceso a datos), es la capa que proporciona a la capa [2] datos prealmacenados (archivos, bases de datos, etc.) y almacena algunos de los resultados proporcionados por la capa [2].

    Existen varias formas de implementar la capa [DAO]. Veamos algunas de ellas:

    La capa [JDBC] anterior es la capa estándar que se utiliza en Java para acceder a las bases de datos. Aísla la capa [DAO] del SGBD que gestiona la base de datos. En teoría, se puede cambiar de SGBD sin modificar el código de la capa [DAO]. A pesar de esta ventaja, la API JDBC presenta ciertos inconvenientes:

    • Es probable que todas las operaciones en el SGBD lancen la excepción SQLException. Esto obliga al código de llamada (la capa [DAO] en este caso) a envolverlas en bloques try/catch, lo que hace que el código resulte bastante prolijo.
    • La capa [DAO] no es completamente independiente del SGBD. Por ejemplo, los SGBD tienen métodos propios para generar automáticamente valores de clave primaria que la capa [DAO] no puede ignorar. Por lo tanto, al insertar un registro:
      • Con Oracle, la capa [DAO] debe obtener primero un valor para la clave primaria del registro y, a continuación, insertar el registro.
      • Con SQL Server, la capa [DAO] inserta el registro, al que el SGBD asigna automáticamente un valor de clave primaria, valor que se devuelve a la capa [DAO].

    Estas diferencias pueden eliminarse utilizando procedimientos almacenados. En el ejemplo anterior, la capa [DAO] llamará a un procedimiento almacenado en Oracle o SQL Server que tenga en cuenta las características específicas del SGBD. Estos quedarán ocultos a la capa [DAO]. No obstante, aunque cambiar el SGBD no requerirá reescribir la capa [DAO], sí será necesario reescribir los procedimientos almacenados. Esto puede no considerarse un factor decisivo.

    Se han realizado numerosos esfuerzos para aislar la capa [DAO] de los aspectos propietarios de los SGBD. Una solución que ha tenido mucho éxito en este ámbito en los últimos años es Hibernate:

    La capa [Hibernate] se sitúa entre la capa [DAO] escrita por el desarrollador y la capa [JDBC]. Hibernate es un ORM (mapeador objeto-relacional), una herramienta que sirve de puente entre el mundo relacional de las bases de datos y el de los objetos manipulados por Java. El desarrollador de la capa [DAO] ya no ve la capa [JDBC] ni las tablas de la base de datos cuyo contenido desea utilizar. Solo ve la representación objetual de la base de datos, proporcionada por la capa [Hibernate]. El puente entre las tablas de la base de datos y los objetos manipulados por la capa [DAO] se establece principalmente de dos maneras:

    • a través de archivos de configuración de estilo XML
    • a través de anotaciones Java en el código, una técnica disponible solo desde JDK 1.5

    La capa [Hibernate] es una capa de abstracción diseñada para ser lo más transparente posible. El escenario ideal es que el desarrollador de la capa [DAO] no sea en absoluto consciente de que está trabajando con una base de datos. Esto es factible si no es él quien escribe la configuración que une los mundos relacional y orientado a objetos. Configurar este puente es bastante delicado y requiere cierta experiencia.

    La capa de objetos [4], que refleja la base de datos, se denomina «contexto de persistencia». Una capa [DAO] basada en Hibernate realiza operaciones de persistencia (CRUD: crear, leer, actualizar, eliminar) sobre los objetos del contexto de persistencia; Hibernate traduce estas operaciones a sentencias SQL que ejecuta la capa JDBC. Para las operaciones de consulta de la base de datos (SQL SELECT), Hibernate proporciona a los desarrolladores un HQL (Hibernate Query Language) para consultar el contexto de persistencia [4] en lugar de la propia base de datos.

    Hibernate es popular, pero complejo de dominar. La curva de aprendizaje, que a menudo se presenta como fácil, es en realidad bastante pronunciada. En cuanto se tiene una base de datos con tablas que presentan relaciones uno a muchos o muchos a muchos, la configuración del puente relacional/objeto queda fuera del alcance del principiante medio. Los errores de configuración pueden dar lugar a aplicaciones con un rendimiento deficiente.

    A la luz del éxito de los productos ORM, Sun, el creador de Java, decidió estandarizar una capa ORM mediante una especificación llamada JPA (Java Persistence API), que se lanzó junto con Java 5. La especificación JPA ha sido implementada por diversos productos: Hibernate, TopLink, EclipseLink, OpenJPA, etc. Con JPA, la arquitectura anterior se convierte en la siguiente:

    La capa [DAO] interactúa ahora con la especificación JPA, un conjunto de interfaces. Los desarrolladores han ganado en términos de estandarización. Anteriormente, si un desarrollador cambiaba su capa ORM, también tenía que cambiar su capa [DAO], que se había escrito para interactuar con un ORM específico. Ahora, escribirán una capa [DAO] que interactúe con una capa JPA. Independientemente del producto que implemente la capa JPA, la interfaz que se presenta a la capa [DAO] sigue siendo la misma.

    En este documento, utilizaremos una capa [DAO] construida sobre una capa JPA/Hibernate o JPA/EclipseLink. También utilizaremos el marco Spring 2.8 para enlazar estas capas entre sí.

    La principal ventaja de Spring es que permite vincular capas mediante la configuración en lugar de hacerlo en el código. Así, si es necesario sustituir la implementación de JPA/Hibernate por una implementación de Hibernate sin JPA —por ejemplo, porque la aplicación se ejecuta en un entorno JDK 1.4 que no es compatible con JPA—, este cambio en la implementación de la capa [DAO] no afecta al código de la capa [de negocio]. Solo es necesario modificar el archivo de configuración de Spring que vincula las capas entre sí.

    Con Java EE 5, existe otra solución: implementar las capas [de negocio] y [DAO] utilizando EJB3 (Enterprise JavaBeans versión 3):

    Veremos que esta solución no difiere mucho de la que utiliza Spring. El entorno Java EE 5 está disponible en los denominados servidores de aplicaciones, como Sun Application Server 9.x (Glassfish), JBoss Application Server, Oracle Container for Java (OC4J), etc. Un servidor de aplicaciones es, en esencia, un servidor de aplicaciones web. También existen los denominados entornos EE 5 «autónomos», es decir, aquellos que pueden utilizarse fuera de un servidor de aplicaciones. Este es el caso de JBoss EJB3 u OpenEJB.

    En un entorno EE5, las capas se implementan mediante objetos denominados EJB (Enterprise Java Beans). En versiones anteriores de EE, los EJB (EJB 2.x) eran conocidos por ser difíciles de implementar y probar, y en ocasiones ofrecían un rendimiento inferior al esperado. Se distingue entre los beans «entidad» de EJB 2.x y los beans «sesión» de EJB 2.x. En resumen, una «entidad» EJB 2.x corresponde a una fila de una tabla de base de datos, y una «sesión» EJB 2.x es un objeto utilizado para implementar las capas de [lógica de negocio] y [DAO] de una arquitectura multicapa. Una de las principales críticas a las capas implementadas con EJB es que solo pueden utilizarse dentro de contenedores EJB, un servicio proporcionado por el entorno EE (Enterprise Edition). Este entorno, cuya configuración es más compleja que la de un entorno SE (Standard Edition), puede disuadir a los desarrolladores de realizar pruebas con frecuencia. No obstante, existen entornos de desarrollo Java que facilitan el uso de un servidor de aplicaciones al automatizar la implementación de EJB en el servidor: Eclipse, NetBeans, JDeveloper, IntelliJ IDEA. En este caso, utilizaremos NetBeans 6.8 y el servidor de aplicaciones GlassFish v3.

    El marco Spring se creó como respuesta a la complejidad de EJB2. En un entorno SE, Spring proporciona un número significativo de los servicios que suelen ofrecer los entornos EE. Por ejemplo, en la sección «Persistencia de datos», Spring proporciona los grupos de conexiones y los gestores de transacciones que requieren las aplicaciones. La aparición de Spring ha fomentado una cultura de pruebas unitarias, que se ha vuelto más fácil de implementar en el contexto SE que en el contexto EE. Spring permite la implementación de capas de aplicación utilizando objetos Java estándar (POJO, Plain Old/Ordinary Java Object), lo que permite su reutilización en otros contextos. Por último, integra numerosas herramientas de terceros de forma bastante transparente, en particular herramientas de persistencia como Hibernate, EclipseLink, iBatis, ...

    Java EE 5 se diseñó para subsanar las deficiencias de la especificación EJB 2. EJB 2.x ha evolucionado hasta convertirse en EJB 3. Se trata de POJO anotados con etiquetas que los convierten en objetos especiales cuando se encuentran dentro de un contenedor EJB 3. Dentro del contenedor, el EJB 3 puede aprovechar los servicios del contenedor (grupo de conexiones, gestor de transacciones, etc.). Fuera del contenedor EJB 3, el EJB 3 se convierte en un objeto Java estándar. Sus anotaciones EJB se ignoran.

    Anteriormente, hemos representado Spring y un contenedor EJB 3 como una posible infraestructura (marco) para nuestra arquitectura multicapa. Es esta infraestructura la que proporcionará los servicios que necesitamos: un grupo de conexiones y un gestor de transacciones.

    • Con Spring, las capas se implementarán utilizando POJO. Estos tendrán acceso a los servicios de Spring (pool de conexiones, gestor de transacciones) a través de la inyección de dependencias en estos POJO: al construirlos, Spring inyecta referencias a los servicios que necesitarán.
    • Con el contenedor EJB3, las capas se implementarán utilizando EJB. Una arquitectura en capas implementada con EJB3 no es muy diferente de una implementada con POJO instanciados por Spring. Encontraremos muchas similitudes.
